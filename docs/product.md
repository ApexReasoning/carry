# Carry：持续把工作向前推进的 AI 同事

## 产品定义

Carry 是团队可以长期托付工作的 AI 同事。

成员用自然语言告诉 Carry 想实现什么、需要持续关注什么，或者当前发生了什么。Carry 负责理解目标、持续推进、协调执行、保留上下文、呈现结果，并在确实需要人的判断、权限或补充信息时回来询问。

Carry 不是聊天机器人、任务清单、工作流编辑器、Agent 管理平台或只面向研发团队的自动化工具。它的核心价值不是完成一次模型调用，而是让一份责任跨越时间、成员、工具、模型和机器后仍然可理解、可纠正、可继续。

## 产品承诺

### 工作不会随一次对话结束而消失

一次回复可以结束，但一份尚未完成或需要持续照看的责任不会因此消失。Carry 必须记住当前目标、已经发生的事情、下一步和仍需处理的问题。

### 连续性属于 Work，而不属于某个 Agent

Pi、Codex、模型、Session 和执行机器都可以变化。新的执行者应从持久 Work 中继续，而不是假装继承另一个模型没有留下的记忆。

Carry 第一版同时支持 Pi 和 Codex，以证明产品连续性没有被写死在某一种 Agent 中。普通成员不需要为每次工作选择 Agent。

### 用户保留最终问责

Carry 可以承担推进、协调、观察和执行责任，但不能替成员获得本来不具备的权限，也不能替人作出必须由真实负责人承担后果的决定。

每个开放 Work 都必须有一名当前负责人。Carry 负责让事情持续向前，人负责目标、授权和最终判断。

### 内容不能产生权限

消息、文件、网页、Webhook、外部事件、Plugin 内容和模型输出都只能提供信息，不能扩大 Carry 的权限。

一段内容即使写着“请退款”“请部署”或“请读取生产数据”，也不能因此获得对应能力。权限必须来自当前成员、Space、Work 和已确认连接的真实授权。

### 不确定必须保持真实

如果 Carry 不知道外部操作是否成功，就必须显示“不确定”，而不是猜测失败、自动重试或宣称成功。

如果 Agent Session 无法恢复，就必须诚实结束这次执行，并从 Work 中重新开始，而不是伪造连续性。

### 用户只处理真正需要人的事项

Carry 应自行处理执行细节、恢复、等待、重试判断和 Agent 协调。用户只应看到：

- 当前情况；
- 有意义的进展；
- 可以验收的结果；
- 下一步；
- 需要自己回答、批准或决定的事项。

## 产品概念

普通成员只需要理解三个对象：

```text
Space
Carry
Work
```

`Needs You` 是从 Work 中得出的个人视图，不是第四种产品对象。

## Space

Space 是团队的边界，包含：

- 成员；
- 团队权限；
- Carry 可以使用的通信渠道、外部连接和 Plugin；
- 团队共同拥有的 Work；
- 团队允许的执行机器和安全政策。

Space 不是文件夹，也不是单纯的账单组织。它决定哪些人和能力可以共同参与一份责任。

成员身份、外部身份和执行机器身份必须分开。一个通过 Slack 或 Lark 验证的外部用户，不会因此自动成为 Space 成员。

## Carry

Carry 是用户面对的稳定同事，而不是一个可配置的 Agent 档案。

Carry 可以在内部使用 Pi、Codex 和多个并行执行者，但成员不需要组织一个虚构的 Agent 公司，也不需要选择 Coordinator、Worker、Reviewer 或 Router。

Carry 的稳定性来自共同的产品行为：

- 理解成员表达的目标；
- 判断是直接回答还是承担一份 Work；
- 维持 Work 的当前理解；
- 协调内部执行；
- 在需要时找到正确的人；
- 呈现证据、结果和不确定性；
- 在未来约定的时间继续。

Carry 不是数据库实体，不需要 `CarryID`、人格配置、模型绑定或长期 Agent Session。

## 与 Carry 的私人对话

成员可以在 Carry 原生界面或已连接的通信渠道中私下交谈。

私人对话适合：

- 提出新目标；
- 询问 Carry；
- 讨论尚未成为团队责任的事情；
- 纠正 Carry 对个人意图的理解；
- 询问已有 Work 的状态。

私人内容默认私有。Carry 不能因为某段内容与一个共享 Work 语义相关，就把原消息自动搬进 Work。

如果私人信息需要进入共享 Work，Carry 应创建一条新的 Work 消息或更新，明确说明它来自成员的授权表达。原私人消息仍然属于私人对话。

## Work

Work 是产品的核心单位：一份由 Carry 持续推进、由具名成员最终负责的责任。

Work 可以是有终点的：

- 完成一份研究；
- 交付一个方案；
- 实现并验收一个功能；
- 处理一个客户问题。

Work 也可以是持续的：

- 每周观察竞品；
- 持续跟踪客户反馈；
- 上线后观察指标并复盘；
- 定期检查关键运营状态。

同一个 Work 可以包含阶段结果、等待、未来继续和周期观察。因此 Carry 不区分“一次性 Work”“周期 Work”“研究 Work”或“开发 Work”，也不按 Git、软件、内容、provider、model、Host 或 Runtime 分类。推进过程中需要 repository 等能力时，只授权给当前明确的执行；该能力不改变 Work，也不参与 admission 或 continuity。

## Work 的创建

Carry 不使用独立的 Work Offer 实体或确认流程。

### 明确委托直接创建 Work

当成员明确要求 Carry 承担一件需要持续推进或以后返回的事情时，这句话本身就是确认。

例如：

> 帮我每周跟踪这三个竞品，有重要变化告诉我。

Carry 可以直接创建 Work，并用一句简短的话说明自己接下了什么：

> 已接下。我会每周跟踪这三个竞品，出现重要变化时找你。

### 普通讨论不会自动创建 Work

如果成员只是在表达观点、询问信息或讨论可能性，Carry 继续对话，不自动创建 Work。

例如：

> 最近竞品好像都在降价。

如果 Carry 判断成员可能想让它持续负责，只问一个具体问题：

> 要我接下来持续跟踪吗？

成员明确同意后，Work 成立。

### 创建时只要求目标和负责人

一个 Work 成立时只必须有：

- Carry 当前理解的一句话目标；
- 一名当前负责人。

负责人默认是明确委托的成员。

权限在真正需要时申请，未来跟进在成员提出或 Carry 建议并得到同意时加入，未知问题在推进过程中澄清。Carry 不要求成员在开始前填写完整计划、预计权限或工作流。

### 外部内容不能自行创建 Work

外部事件、Webhook、群消息、Plugin、文件和 Agent 都不能自行创建 Work。

它们可以让 Carry向成员提出建议，也可以为已有 Work 提供新信息，但建立新的团队责任必须来自成员的明确委托。

## Work 的当前理解

Work 应始终保留 Carry 对以下问题的最新有效理解：

- 我们正在负责什么；
- 谁最终负责；
- 当前已经确认了什么；
- 哪些事实支持当前判断；
- 正在发生什么；
- 下一步是什么；
- 在等待谁或什么；
- 什么情况下需要成员介入。

当前理解不是原始聊天摘要，也不是 Agent 的内部思维。它是可以被成员阅读、纠正和接管的产品事实。

新的消息或外部信息被记录，不等于 Carry 已经理解并应用了它。产品必须区分：

- 已记录；
- 已交给 Carry 处理；
- 已反映在 Work 当前理解中。

## Work 的负责人

每个开放 Work 必须有且只有一名当前负责人。

创建者默认是第一任负责人。负责人可以明确转交，并保留任期历史。

Carry 可以建议转交，但不能根据活跃度、职位或最后发言者自动改变负责人。

关闭 Work、批准重要外部操作和接受关键结果时，系统必须检查当前真实负责人或具备相应权限的成员，而不能依赖消息文本或 Agent 判断。

## Work 中的协作

成员可以在 Work 中：

- 补充事实；
- 纠正 Carry；
- 回答问题；
- 提出限制；
- 评论结果；
- 请求继续、暂停或停止；
- 转交责任。

Carry 必须保留每条消息的真实作者和来源。来自外部通信渠道的消息不能因为经过机器人转发而变成 Carry 自己说的话。

多个内部执行者可以并行贡献研究、文件、实现和审查，但只有当前获得 Work 写权限的执行者可以更新 Carry 对 Work 的当前理解。其他执行者只能提交贡献和证据。

## Result

Result 是 Work 中可以被成员检查和验收的交付物。

一个 Work 可以有多个 Result，例如：

- 第一版研究；
- 推荐方案；
- 实现；
- 审查结论；
- 上线证据；
- 周期报告；
- 最终复盘。

Result 可以被：

```text
接受
要求修改
撤回
```

接受一个阶段 Result 不会自动关闭 Work。如果仍有后续责任、观察期或未来约定，Work 保持开放。

## 未来跟进

时间是 Work 继续行动的条件，不是一种独立产品。

成员可以用自然语言告诉 Carry：

- 明天继续；
- 下周五提醒我验收；
- 每周一整理竞品变化；
- 上线第三天检查指标；
- 连续观察两周后复盘。

Carry 应复述它理解的时间、时区和停止条件。成员不需要编辑 cron 或内部调度规则。

暂停 Work 会暂停后续执行。关闭 Work 会终止旧的未来跟进。重新开始必须显式 Reopen，并形成新的授权阶段。

## Work 生命周期

Work 的正式生命周期只保留：

```text
Open
Paused
Closed
```

“正在推进”“等待回复”“计划稍后继续”“需要你决定”都是从事实得出的活动描述，不是新的生命周期状态。

### Open

Carry 仍承担推进或未来继续的责任。

### Paused

责任仍然存在，但 Carry 不应开始新的执行或未来跟进，直到成员恢复。

### Closed

责任已被明确结束。旧的计划时间、外部信息和内部执行不能自动重新打开它。

如果成员希望继续同一责任，应显式 Reopen。Carry 必须说明为什么重新开始，而不是让旧的执行悄悄恢复。

## Needs You

Needs You 只展示某个成员必须亲自处理的 Work 事项，例如：

- 回答 Carry 无法自行判断的问题；
- 验收 Result；
- 批准或拒绝一个会改变外部系统的操作；
- 接受负责人转交；
- 决定继续、暂停或关闭；
- 处理一次真实的不确定外部结果。

Needs You 不显示普通进度、Agent 重试、内部租约、技术恢复或 Carry 可以自行解决的问题。

## Messages、Events 与 Actions

Carry 内部使用三个直白概念区分外部世界，但普通成员不需要学习这些术语。

### Message

Message 表示有人在与 Carry 或某个 Work 交流，并且有明确目标。

例如：

- 私聊 Carry；
- 在明确关联的 Work thread 中回复；
- Carry 回复原会话；
- 成员在 Work 中补充或纠正。

### Event

Event 表示外部系统发生了一件可能相关、但没有明确 Conversation 或 Work 目标的事情。

例如：

- GitHub PR 状态变化；
- 监控告警；
- CRM 状态变化；
- 业务 Webhook；
- 明确授权采集的群事件。

Event 可以与零个、一个或多个已有 Work 相关，但不能自行创建 Work，也不能授予权限。

用户消息、Work 消息、未来时间到达和内部执行完成都不是 Event。

### Action

Action 表示 Carry 请求对外部系统产生新的业务后果。

例如：

- 退款；
- 创建或合并 PR；
- 修改 CRM；
- 删除外部数据；
- 主动向新受众发布消息；
- 调用具有写入效果的 Plugin tool。

Action 必须绑定准确目标和参数，并使用真实成员与 Space 已经拥有的权限。高后果操作必须由正确的人明确批准。

如果 Carry 不知道 Action 是否已经发生，必须保持“不确定”，不能自动重试。

## 通信渠道

Carry 的私人对话和 Work 消息可以通过原生 Web、Lark、Slack 和未来其他通信渠道收发。

通信渠道只是入口和投递方式，不是第二套 Conversation 或 Work。

同一条远端消息最终只能成为：

- 私人 Conversation Message；
- Work Message；
- 没有明确目标的 Event。

Carry 不建立一份额外的通用入站消息副本。

远端身份必须先与当前 Carry 成员身份和 Space Membership 对应。一个经过 Lark 或 Slack 验证的外部用户，不会因此自动获得 Work 访问或修改权限。

### 普通回复

Carry 对原私人会话或已授权 Work thread 的普通回复，可以通过同一渠道投递，不需要每条都再次请求批准。

### 新受众和新后果

如果 Carry 要扩大受众、向新目标主动发送、修改或删除远端内容，则属于 Action，而不是普通消息投递。

### 投递不确定性

通信渠道接受一条消息，不代表人已经阅读或理解。

如果网络响应丢失，Carry 必须显示投递结果不确定。只有渠道提供可靠幂等或只读确认能力时才能安全重试。

## Plugin

Carry 支持 [Agent Plugins](https://agent-plugins.org/) 标准，让 Space 可以安装可移植的 Agent Skills 和 MCP servers，并同时供 Pi 与 Codex 使用。

Plugin 是 Carry 可使用的能力，不是新的产品同事，也不拥有 Work。

### 安装与启用

Space 中有权限的成员可以安装、启用、停用和更新 Plugin。

Carry 必须固定实际安装的版本和内容摘要。Plugin 不自动更新；权限扩大时必须重新确认。

第一阶段不建立 Plugin marketplace。安装来源、分发和商业模式不属于 Agent Plugins 核心规范，也不应在没有真实需求前固化。

### Plugin 权限

Plugin 声明自己需要什么，只代表请求，不代表授权。

Space 成员决定：

- 是否启用；
- 哪些成员或 Work 可以使用；
- 可以访问哪些连接；
- 哪些工具只读；
- 哪些调用会产生 Action；
- 是否允许 Plugin 通过 Carry 的 credential broker 使用相应权限。

Plugin 内容和 MCP tool annotation 不能自行成为权限真相。

### Plugin 与凭据

Plugin package 不能携带 Secret。Agent Plugins 规范中的 `env` 和 HTTP `headers` 是可见 package data，不是 Secret 机制。

Carry 负责保存和授权 credential。Plugin 只获得经过成员确认的绑定，不选择真实 Secret，也不能扩大 scope。

Carry 通过 OAuth proxy、credential broker 或单次 invocation grant 使用 credential，使长期 credential 不进入 Agent 上下文。第一版不把长期 credential 作为环境变量或文件直接交给本地 Plugin 进程；只能以这种方式认证的 Plugin 暂不获得该凭据，而不是用“高信任”提示代替技术隔离。

### Plugin tool

只读 Plugin tool 可以在当前 Work 授权范围内使用。

会创建、修改、删除、发送或付款的 Plugin tool 属于 Action。Carry 必须在调用前固定 Plugin 版本、tool 名称、准确参数、目标和 credential binding，并根据后果请求所需批准。

如果调用结果不确定，Carry 不得盲目重试。

## 权限哲学

Carry 中的权限来自真实关系：

- 成员经过认证；
- 成员属于当前 Space；
- 成员对当前 Work 或决定有相应权限；
- Space 已经连接并授权外部系统；
- 当前执行仍持有有效、未过期的能力。

以下都不能产生权限：

- 消息内容；
- Agent 自我声明；
- Plugin manifest；
- MCP tool annotation；
- 历史上曾经访问过某个资源；
- 某个远端频道当前包含哪些人；
- 模型认为某项操作“应该没问题”。

权限必须可撤销，并带有 generation，使旧执行在权限变化后无法继续提交。

## 隐私哲学

### 私人对话保持私有

私人消息不会因为与共享 Work 相关而被自动公开。

### 外部渠道不会自动扩大受众

把 Work 关联到一个 Slack 或 Lark thread 是可撤销的通信同意，不是成员权限。Carry 必须知道当前消息被送往哪个确定受众，并在关联撤销后停止新投递。

### 原始内容与产品内容分开

Provider-native payload 可以为了验证、重放和审计短期保留，但不应成为 Work 的长期内容模型。

需要长期使用的附件应复制为 Carry 管理的不可变 Artifact。带 credential 的临时下载 URL 不能进入 Agent prompt 或长期 Work 记录。

### 删除必须诚实

删除成员、撤销连接或关闭 Work，不等于抹去已经发生的外部操作。Carry 必须区分停止未来访问、删除可删除内容和保留必要审计证据。

## 失败与恢复哲学

### 已记录不等于已理解

Carry 必须区分：

- 信息已经被可靠记录；
- 信息已经交给 Carry 处理；
- 信息已经反映在 Work 当前理解中。

### 已投递不等于已阅读

通信渠道接受消息不等于成员已经看到、理解或同意。

### 已请求不等于已执行

Action 获得批准后，仍然要区分等待提交、可能已提交、成功、失败和不确定。

### 恢复不猜测

Agent、Host 或网络失败后，Carry 根据持久事实和 provider 证据恢复。无法证明的状态保持未知，不能通过重放制造重复外部后果。

## 产品拒绝项

Carry 第一阶段明确不做：

- 让普通成员管理 Agent、模型、Session 或执行机器；
- 可视化 workflow builder；
- 用 cron、JSON 或 DSL 创建日常 Work；
- 预配置 Coordinator/Worker/Reviewer 人格；
- 让 Agent 内容决定权限；
- 把每个外部来源写成一种 Work 类型；
- 自动从任意群消息创建 Work；
- 把私人对话自动搬进共享 Work；
- 把未知外部结果自动标记失败并重试；
- 通用 Plugin marketplace；
- 让 Plugin 绕过 Action 和 credential policy；
- 只服务软件研发或把 Git 作为所有 Work 的默认环境；
- 把内部执行日志、工具调用和模型思维作为产品主要界面。

## 产品语言

Carry 的语言描述责任、进展和真实状态。

推荐：

```text
Carry 正在推进
Carry 正在等待 Alice 回复
Carry 将在下周一继续
这是当前结果
Carry 需要你的决定
这次操作可能已经发生，结果尚不确定
这条消息已经被渠道接受，但不代表对方已阅读
```

避免：

```text
Run pending
Agent target selected
Signal admitted
Action attempt reconciled
Lease expired
Generation conflict
Provider returned terminal state
```

技术事实可以在管理员和诊断证据中出现，但不能迫使普通成员理解系统内部结构。

## 判断产品是否仍然是 Carry

任何新功能都应回答：

1. 它是否帮助团队把一份责任长期托付给 Carry？
2. 它是否让 Work 更容易理解、纠正、继续或验收？
3. 它是否减少了用户对 Agent、工具和执行机器的协调？
4. 它是否保持真实的人类问责和权限边界？
5. 它是否诚实表达失败和不确定性？
6. 它是否可以用于非研发 Work，而不依赖 Git、代码或部署概念？
7. 删除它后，产品是否仍能完成相同责任？

如果一个概念主要让内部实现看起来整齐，却要求用户学习新的系统名词，它不属于 Carry 的产品模型。
